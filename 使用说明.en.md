## First use: give an agent a clear task and keep its record

This workbench helps you define goals, keep materials, prepare instructions and inspect results. The agent you choose does the work. Start with one small task with a clear acceptance check, then widen the scope.

### 1. Start from the right template

- General template: shared governance, notes, file reading, skills, tools and automation, without business materials. Add your own DIY modules.
- Three-business template: the shared workbench plus Paper Writing, Video Editing and Novel Writing with stage skills. Use the business you need; you do not have to use all three.
- Existing research templates and Literature, Experiments or Paper modules remain available. They are existing materials or the older template, rather than extra default navigation modules in the new three-business template.

Confirm the source template, then run 新项目.bat, or enter a name and location under Settings → Built-in and choose New project. The new project inherits its source template configuration. Built-in folders are included; choose extra materials in the Custom dialog for this copy only. A project without template configuration follows its own built-in copying rules. Its name alone does not establish that it is a general or business template.

Run 启动.bat inside the new project. Check the project name and location at the top to confirm which project is open. Bundled instructions do not mean software, accounts or machine settings have been configured.

### 2. Write the need and its acceptance criteria before adding modules

In Blueprint, describe the overall aim and create a requirement. State the current problem, the result you want, how to check it, and which materials may be used. A requirement can be saved before any module exists and later assigned to one or several modules.

For example: “Edit this authorized video into 30 seconds, preserve the original, and deliver a 1080p MP4 with captions. Check duration, resolution, captions and source credits.” This gives an agent more to act on than “make the video look better.”

If the direction is undecided, keep it in Ideas until you confirm its destination. Notes and business files stay in their original locations; Blueprint shows their associations without making several copies of a requirement.

### 3. Choose the current stage skill and check inputs and tools

In Skills, choose a business and then a stage. Read its inputs, expected outputs, acceptance criteria and the condition for continuing.

| Business | Typical route |
|---|---|
| Paper Writing | Topic and hypothesis → literature and evidence → data and experiment design → reproduction and runs → results and figures → manuscript and citations → submission preparation → revision and response. Use presentation and discussion when needed. |
| Video Editing | Sources and rights → probe and specifications → script and timeline → local editing → audio and captions → preview and acceptance → export and provenance. |
| Novel Writing | Brief and reader → world and characters → layered outline → draft and state → continuity and cold read → author-approved revision → handoff and manuscript. |

Open an entry for its Chinese or English text, source, license, supporting files and dependencies. Project files are the originals, readable by different agents without reinstalling them for every agent. Optional installation creates a copy for agents that support automatic discovery.

A link-only entry describes an external project and provides its official link; it is not an installable skill. Missing text, licenses or supporting files are reported as gaps. If a skill needs FFmpeg, Python or another tool, read the domestic or international route in Tools and verify the actual environment. A light or illustration does not prove installation, sign-in or available quota.

### 4. Give an agent one well-defined task

Turn a confirmed requirement into tasks with checks. Prepare materials in a Work order and organize the instruction. Ask the agent to read this project's AGENTS.md and its workbench skill first. MCP reads the same records; an agent without MCP can read the ordinary files directly.

Copy this outline and fill it with the actual task:

> Goal and task: full identifier and source file. Requirement and acceptance criteria: the corresponding Blueprint record. Stage and skill: the selected entry and file. Inputs: authorized files, data or manuscript versions. Rules: general, project and module rules. Allowed changes: explicit files and output locations. Check gaps first and submit a construction plan; follow the current review requirements before construction. Deliver the artifacts, actual check results and unfinished work. Put new decisions requiring me in Waiting for you; do not approve them on my behalf. Leave a handover when stopped.

An accurate instruction does not require pasting the whole repository into the conversation. Full identifiers and sources keep historical records with repeated numbers separate.

### 5. Inspect the plan, construction and automatic acceptance

Automation shows tasks, employees, construction plans, windows and deliveries. An employee's roles and allowed scope determine whether it may take a task. When review is required, a different employee with the reviewer role checks the construction plan. Revise a returned plan and wait for approval before construction. Changed file scope requires another review. Core changes require the project's snapshot and core-lock procedure.

The worker delivers artifacts and actual check results. This project enables the `checks-pass` delivery policy: passing every actual check automatically accepts the delivery and marks the task done; failed checks send it back for repair. New deliveries do not wait for another acceptor or your confirmation on each slip. Inspect results and logs when you wish; if something is wrong, send it back with a reason and the agent stops advancing that item to redo it. Never report an unrun check as passed. Keep existing deliveries' acceptance history without asking you to accept them again. Projects without this policy keep the original acceptance workflow.

An existing terminal opens in watch mode. Choose Take control explicitly before typing. Reading a graph, guide or skill does not start employees. Only when you explicitly enable automatic running can the existing dispatch process continue under its roles, review gates, stop conditions and run limits. Actual records establish how far execution has reached.

### 6. Save a checkpoint, leave a handover, then continue

Save a checkpoint after a stage passes. The delivery should say where outputs are, which checks ran and what actually happened. Before another agent takes over, leave a handover with: completed work, changed files, check results, unfinished work, risks and unverified items, the next task, and decisions awaiting you.

The next agent reads the latest handover, then the task, requirement, plan, applicable rules and actual outputs. Plans describe intended work, logs describe events and deliveries describe results. Old conversation alone does not establish the project's current state.

### Reading the interface

Collapse the left directory to give its space to the content. Zen hides navigation and the left directory while keeping the main area's available width. Prose keeps a comfortable line length; diagrams, file previews and two-column readers use the available width. Details, terminals and sticky notes remain available. Leaving Zen restores the previous layout. Fullscreen notes, movable details and collapsed small windows retain their existing controls.

Notebook holds lasting records; Sticky note captures the current page. Automation logs are separate from human notes. Keep unknown checks unknown and mark passed only after an actual result.

## One line: ideas → needs → blueprint → rules

Two layers:
- **Framework** (direction; you decide or authorize an agent to edit): the framework blueprint = S0 and S1 in `治理/目标/`; framework rules = general and project
- **Modules** (what we do now: renovate one module at a time): three record types in the central governance directory — `需求.md` needs (what it should do and the effect you want — this sets the direction of the work) · `蓝图.md` blueprint (the items to build for those needs) · `戒律.md` rules

**Ideas**: first on the second bar. Everything you say in passing goes into one table, `资料/想法/想法.md`, numbered 想-1, 想-2 …
- In the sidebar, **Idea repository** opens discussion records and **Requirements** opens all central requirements. Create, edit, and assign goals or modules there; Ideas, Blueprint, and MCP share the same files in `治理/需求/`. A requirement can exist before any module is assigned.
- How they come in: click "Idea" in the note window before saving (the note is saved as usual and the idea table gets a line linking back) · "Make it an idea" on an older note in the notebook · "+ New idea" on the Ideas page · what you tell an agent, it records too
- How they become needs: the agent writes 1–3 destination candidates per idea, each with a one-line reason; you click "This one" —
  - Module need: a new one, or added to an existing one, written into the central requirement source file (marked "from 想-3")
  - Module rule: written into its central module rule file
  - Framework layer (S0, S1, general / project rules): only marked and sent to Q&A for you to change yourself
  - Or skip the candidates: "Later", "Drop" — kept, never deleted
- The Ideas page groups them by destination: to sort (those with candidates first) · for you (framework) · became needs · became rules · later · dropped

**Module needs** (`治理/需求/<source>.md`): one bold line "what it should become" · which framework goals it serves (S1 codes) · your own words · a table `| 需-1 | function | effect (what you see when you open it) | from |`. You decide it and can edit it in the web UI or authorize an agent to write through MCP; no status column — a need counts as met once every item built for it is accepted.
**Module blueprint** (`治理/任务/<source>.md`): one line "怎么算装好：" plus a table `| S2-1 | what | for (需-1) | check | status |`; agents may propose items (status "没做"), you nod. Refer to them with the module name: "文献 需-2", "文献 S2-3".
- Needs, acceptance criteria, rules, tasks and plans are viewed centrally in Blueprint. Module pages show business materials and module skills; old needs links redirect to Blueprint.
- Use New need in Blueprint before a module exists, then assign modules when ready.

## Goals: the blueprint

The second bar's Blueprint opens **Project panorama**: S0 above S1 goals, with modules below. Select a goal to see its linked modules; select a module to see supported goals, tasks, plans and link sources. Expand S2 tasks on demand. Original goal files and historical files remain in the left column.
- Modules have three layers, from top to bottom: **General operations → Project governance → DIY workloads**. General operations include the app's existing search, notes, plans, Q&A, automation, snapshots, skills and tools. The middle layer contains Ideas, Blueprint, Rules and Code. These capability layers do not move the three navigation bars.
- General modules come from the app's built-in list and open the existing pages; they do not create duplicate folders under `资料/`. Explicit references such as `通用/笔记本` or `通用/计划` in a goal or plan's module field distinguish them from DIY modules with the same name. Without a recorded link they remain unlinked.
- Each S1 is one short file with a table of S2s; the last cell says the status (done / doing / not yet / later)
- **Status is written only at the bottom level**: whether an S1 is done is worked out from its S2s, never typed by hand
- Links come only from explicit goal-module fields, module needs' goal references, or plan header metadata and goal folder attribution. Mentions in prose do not count. Guessed or unconfirmed references are flagged rather than accepted. Historical "所有模块" continues to mean project folder modules; "所有通用模块" means the general operations layer. Every link has source references.
- Missing needs, blueprints and links are shown separately, including empty templates. Module tasks and tasks under supported goals remain separate: support is neither task assignment nor task dependency. This version does not calculate a critical path.
- Done and awaiting review have separate counts, read from S2 records. The top review link counts delivery records; task counts may differ. The website and MCP `get_overview` share the same panorama data.
- S0, S1 and module needs use your own words and you can edit them directly or authorize an agent to write through MCP; new directions still require your decision
- **Big problem cards**: under S0, one card per big problem: how many parts, how many finalized, items done / total (the same numbers as the Automation overview). Click one to highlight its goals and modules; click again to clear. Modules with tasks that the S0 table does not list get their own card
- **Where it is stuck**: below the goals, unfinished items grouped by the need they serve, the heaviest first; items that name no need come last. Click one to open its goal or module
- **Structure · Time**: under the big problem cards. **Time** lists every item by the last change to its line (delivered, status changed, added), newest first, split by day, with the time, item, work, status and who changed it (from the local git; lines not committed yet use the file time)
- **Down to the delivery**: a status such as `J25` in the task tables links to that delivery, which shows the item's history and its local git commit
- **Drafts**: when an agent wants to add a task or a need while working, it does not edit the real files; it puts a draft in the draft area (`治理/草稿/草-1.md`, one file each). When drafts are waiting, the blueprint shows a "Drafts" block at the top: where it goes, who proposed it, why, and what it says. **行** takes it into the real task / need table (numbered in order, status "没做"); **改一下** lets you edit first; **不要** keeps the record without taking it in. **When there is a reviewing agent** (a profile with the Review role, 10-02 S1-8 S2-40), drafts go to it first and each card says where review stands: waiting for the reviewing agent · reviewed: approved, with the reason · sent back, waiting for the author (who edits the same draft for another round) · three rounds failed, over to you. You can still click 行 or 不要 at any time, reviewed or not; for an item taken in this way, its right panel says who drafted it and what the reviewer said
- **Finalize**: open a goal or module; the top of its details says whether it is finalized. If something is missing it says "还缺：…" (no needs, needs without tasks, tasks without a check, no module rules, format problems) and the Finalize button stays disabled until you fill them in. When nothing is missing, type a sentence and click Finalize: the file header gets a line "规划：定稿 · date · 作者：「your words」". **Agents only pick work by themselves from finalized parts**; Unfinalize removes the line (named work still runs). Only you can press it on the page; agents have no tool for it. The "Before full automation" table on the Automation overview has the same button on each row

## Rules

Second bar, 戒律 Rules. The left column has **"Main" on top: `AGENTS.md`** (what an agent reads first, one rule per line), **"Framework rules": 1 general · 2 this project**, each with a count, and **"Modules": each module's own `戒律.md`** (listed automatically, no need to link them).
- A lower layer may only be stricter, never looser; if they clash, the upper layer wins
- A module's own rules live in `戒律.md` inside that module's folder; an agent reads it before working in that module
- The rules a work order keeps are worked out for you: general · project (every order) → the module's → the order's own "never"

## Modules

**Module page**: folder tree on the left (name, size, time), preview on the right. Markdown, web pages, PDFs, images and code open in place. The address bar carries the file you are reading, so a link or the Back button returns to it.
- **Add a module**: in Settings → Modules, "Add a module" at the bottom (name, English name, one line); a folder of that name appears under `资料/`. Folders you create yourself show up within a second or two
- On every module page, "Main" on top: module needs · module blueprint · module rules · module skill (see "One line" above)
- **A module's own skill lives in the module**: `资料/<module>/技能/SKILL.md`, saying how things in this module are done (for Literature: adding papers, writing explanations, whose notes are whose, putting papers on the download list). Agents read it first when they work in the module, and a work order for the module brings it along. Edit it right there
- **源代码 Code**: "Main" on top is the **code map** (10-02, S1-1 S2-21) with two views in the top right. **Map** (default) lays the whole source out as a map you can fly over — one block per file, sized by line count, files of the same folder side by side; each block holds the real code, seen from afar as lines colored by syntax and, zoomed in, as readable text with line numbers. **Wheel** zooms around the mouse, **drag** to move, **double-click** a file to fly to it (or a line, when close enough), **click** to see what it is: its one-line description, line count, how often it changed in git and who changed it last, with Open for the usual reader; the panel also lists its **functions and classes** — click one to draw lines to every place that uses it (mentions in descriptions count too). The bar on top: **find a word** (in file names or code; matching lines turn yellow, Enter flies through them) · four colorings **By type · Recently changed · Changed often** (times changed in git) · **Uncommitted** (lines changed since the last commit get a bar on the left) · **Tilt 3D** (the map tilts back like flying over it; right-drag or Shift-drag to turn, drag up or down to change the angle) · **Overview** (shortcut 0). File contents are fetched only when a block comes into view and kept afterwards, so large projects stay smooth. **List** is the old view: one sentence per program file, read live from its top description. When something breaks, find the part here first
- **Four ways to look at the code map** (10-03, S1-1 S2-24): switch at the left of the top bar — **Importance pyramid** (default) · **Folder steps** · **Change heat** · **Flat map** (the map above, for reading). The first three are 3D steps: one square terrace per tier, the top one smallest and highest, wider further down; each file is a block on its terrace with its code (lines colored by syntax) on top. Importance is computed fresh each time, the same way for any project: **how many other files use it** (Python imports, scripts a page loads, files that mention its full name), **whether it is an entry point**, and **how many tests cover it**; tests and text files go to the bottom. Folder steps puts files near the module root on top; change heat puts the most-changed files on top (by git, or by last change without git). **Left-drag** to turn, **right-drag** (or Shift) to pan, **wheel** to zoom, arrow keys turn too; **click** a block and the panel says which tier it is on and why ("used by 31 files · 39 tests cover it", plus who uses it); click a function there to draw arcs to every block that uses it; **double-click** a block (or Read code) to jump to the flat map zoomed in to readable text. Search matches turn yellow; Enter flies from block to block. **Fullscreen**: the button or F fills the screen with the whole map (bar included); Esc or the button again returns, with the view where you left it
- **Deleting**: nothing is really deleted from the page. "Delete" in Settings → Modules removes an empty folder at once; if it has files you are asked first, then the whole folder moves into `回收站/` (recycle bin) at the project root, where it can be restored
- Files that must stay where they are (code, config) are linked in with a `.链接.txt` in the module folder, one path per line — nothing is moved

## Downloads: papers to fetch, one per line

Literature has two main entries: **Downloads** and **Library**. Downloads accepts a URL or DOI, starts a requested download, and supports PDF upload or drag and drop. Status reflects actual files. Agents can add references to the same list; the local program or the user handles downloads:
- At the top: **downloaded / total** with a progress bar; "Only the missing ones" hides what is done
- **Grouped by publisher** (read from the DOI: Elsevier, Springer · Nature · BMC, IEEE, ACM, Oxford…; anything unrecognised goes under "Other"), each group with one line on where to get it — **log in to a platform once and fetch its papers together**
- One card per paper: title · authors · year · journal (fetched from OpenAlex for papers with a DOI; an agent can also fill them in when adding) · why it is needed · a remark (e.g. "software manual, no PDF needed")
- Each card says what to **save it as** (`原文/下-3 title.pdf`): save it into `原文/` under that name and on the next refresh it is recognised, turns green and joins the library, with authors · year · journal copied into the paper's `信息.json`
- Buttons: **Open DOI** (goes straight there and starts watching Downloads) · Copy DOI · Copy title · Copy file name · Scholar (searches Google Scholar by title); finished cards fade out with the title struck through, and an "Open" button
- Lamp: grey = not yet · **green = downloaded** (the file really is in `资料/文献/原文/` and is a PDF) · red = what came back is not a PDF
- **Download**: lines with a direct PDF link, an arXiv link, or a DOI for which OpenAlex found a legal free copy get a "Download" button; "Download all direct ones" fetches them all. It uses your computer's network settings (works with a proxy on)
- **Download it yourself**: for papers behind your institution's login, open the link and download in your browser. After you click, the program watches your Downloads folder for 10 minutes; a new PDF is copied in and the line turns green (the original stays in Downloads)
- **Tick** = downloaded: got it somewhere else? Tick and pick that PDF (or drag the PDF onto the line)
- The box at the top adds a paper by link or DOI; what an agent adds with `add_download` says it added it and why
- Rule (literature rule 文-9): only legal sources (publishers, arXiv, open access), never around a paywall; PDFs only, 200 MB at most. The list itself is `资料/文献/下载清单.md`; any module with a file of that name gets this page too

## Viewing files in the page: no switching apps

Open a file and it shows — nothing to install, no agent involved (blueprint S1-10):
- **Peek anywhere** (10-01): any project file path written on a page (guides, plans, deliveries, cards — shaded like `工具库/下载/清单.md`) opens in a pop-up with the same viewer as module pages; "写进笔记" and "open in new tab" sit at the top, Esc closes it

- **Contents column** (the left column on every page): drag its right edge to resize, the width is remembered on this computer; hover it for a small arrow that folds it away and back
- New projects get two more starter modules: **Reports** (PPT, talk notes, defence slides) and **Media** (video, recordings, clips, pictures)

## Plugins: heavy work you install yourself

Heavy work stays out of the core as plugins: one folder each, under the app's `插件/` (`插件/<name>/插件.md` says what it does, which outside program it needs and how to install it). Remove the folder and the core carries on without that feature.
- **Install**: the "安装" part of 插件.md is written for an agent — any agent can follow it and asks you before installing anything (what, how big, from where)
- **Enable**: only you can, per project; agents never enable for you. Enabling and disabling go into the log

**PPT预览** (the first plugin): open a PPT and click "用「PPT预览」插件显示原版" → confirm → enabled. From then on a PPT shows two buttons:
- **照原样 (as is)**: PowerPoint on this computer (or LibreOffice) opens it read-only in the background and turns it into a PDF you page through, just like in PowerPoint (no animation). The first time takes a few seconds; unchanged files come straight from `索引/预览缓存/`; the PPT itself is never touched
- **只看字 (text only)**: the same list of text and pictures as without the plugin
- Old .ppt files: the core cannot list their text, but "as is" works
- Neither program on this computer: the page says what is missing; install one following `插件/PPT预览/插件.md`

## Literature: library · reader

**Two folders, matched one to one**: original PDFs live in `资料/文献/原文/` (`L1 title.pdf`); everything that explains a paper lives in `资料/文献/解读/L1 title/` — an `信息.json` (title, authors, DOI, tags, groups, reading state) and three parts: `文本/` (translation, summary, explainer, and any retained legacy notes… one .md each) · `图片/` (images) · `图解/` (interactive 2D/3D diagrams, one idea per .html page).
