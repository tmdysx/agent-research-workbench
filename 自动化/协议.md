# 自动化协议 —— 人和 agent、agent 和 agent 怎么配合

> 正本。`AGENTS.md`、技能「自动化科研交互界面」、W1 卡、接口（MCP）都照这份；跟这份不一样的，以这份为准。
> 作者 2026-09-30：「自动化协议宽松一点，不要老是让人去确认，只有有需求，蓝图，戒律，验收标准，等等可以一站式自动推进进程，人可以慢慢看日志或者成果，或者体验就完事了」「这样到时候你就可以开多个智能体按照相关要求开工……也能让codex也加入一起开发」。
> 作者选的：只在「彻底删除、公开发布」「改方向」停；agent 自己从蓝图挑活；几个 agent 一起干时用本机 git 记谁改了什么。
> 09-30 晚又加：「得给agent注册……要有一个注册档案和编号，职责啥的都可以随着项目变迁」「我还是想让玩家可以自己动手diy」——见第四节「报到和档案」。
> 网页「自动化」分三块：**Agent 管理**（报到、档案、名册、分工规矩、交接单）· **工单**（开工单、流程）· **验收与日志**（交付单、一件的来龙去脉、每圈日志、本机 git）。

**本项目的交付策略（2026-10-07）**：`自动化/交付策略.json`（10-07 统一内置以前在 `自动化/内置/`） 明确写入 `{"version": 1, "mode": "checks-pass"}`。交付有非空检查列表，且每一项 `ok` 都是布尔值 `true`，才自动验收通过、记为做完；不等其他验收岗位或人逐张点确认。失败、未测、缺少 `ok`、字符串或数字都不算通过，交付会自动打回「在做」，agent 修复、实际复验后重交。空检查不许交付；配置畸形或使用链接时，在写交付单前拒绝，不留下半张单。人平时看成果和日志，不满意时打回并写理由，agent 停下推进该件、按理由重做。无此配置的项目保留原验收流程；已有记录按实际历史读取。此策略不免除计划审核、岗位与范围、认领、核心锁、暂停和原停止条件，也不会启动员工或新增验收模块。

## 一、自己能跑，要齐这 7 样

| | 要素 | 是什么 | 在哪 |
|---|---|---|---|
| 1 | 需求 | 为什么做、做成什么效果 | `治理/需求/` |
| 2 | 任务 | 一件件要做的（S2），写着为了哪条需求 | 蓝图：`治理/目标/`、`治理/任务/<模块>.md` |
| 3 | 验收标准 | 每件的「怎么验」，最好机器能查（跑测试、文件在、页面上看得到） | S2 表的「怎么验」一列 |
| 4 | 戒律 | 能做什么、哪几件必停 | `治理/戒律/`、`AGENTS.md` |
| 5 | 工具和材料 | 用什么、在哪、装没装 | `工具库/`、开工单 |
| 6 | 分工 | 谁是谁、归谁管什么、谁在干哪件，别两个人撞一件 | agent 档案 `自动化/agent/`、接口里的认领（网页「自动化 → Agent 管理」） |
| 7 | 记录和退路 | 日志、交付单、交接单、本机 git；存档、回收站、打回 | `笔记/日志/`、`自动化/`、`存档/`、`回收站/` |

缺哪样补哪样。**没写「怎么验」的件 agent 不自己挑**——先把怎么验写上（任务的怎么验 agent 可以写；需求、S0、S1、戒律是方向，只有人改）。

## 二、什么时候自己开工

- 蓝图里写了「怎么验」、还没做完、不是「以后」、不在等（等工具 / 等你 / 待你验收 / 等别的件）的件，agent **自己挑、自己开工单、自己开工**，不用人点「交给 agent」
- **等别的件**：一件要等另一件做完才能做，状态写「等 S2-3」（同一个目标里的）、「等 S1-8 S2-25」「等 工具 S2-5」（别处的）。等的那件没做完不派它；做完了自动能领，不用改状态（10-02，S1-8 S2-35）
- 挑的顺序 = 蓝图的顺序（总蓝图 S1-1… 在前，模块蓝图在后）。**你想先做哪个，在蓝图里把它排到前面**，或在对话里点名
- 一次只跑一张开工单；几个 agent 都在这一张里各领各的件；这张被别人占满了（比如只动一个模块的单，一个模块同时只给一个人），`next_task` 就给你蓝图里别的、不撞道的件先做（不算在这张单里），不闲着。这张里没有能做的了（也没人在做），就放下它、接着开下一个目标的——**一站式往下推**，直到蓝图里没有能自己做的件
- 人在网页上**叫停**过：agent 不再自己开新单，等人再点「交给 agent」，或人在对话里说开工

## 三、一个 agent 一圈怎么走

1. **报到**：第一次来先 `register_agent`（名字、用的哪家、一句话），拿到编号 G 和档案；名字每个 agent 不重复（`claude-code`、`codex`、`cursor`……），同一个程序开了几个一起干的写 `claude-code#1`、`claude-code#2`，调接口时都带上 `agent`。**没报到领不到活**；同名再来接上原来那份
2. **进门先读**：`AGENTS.md` → 你的档案（`my_profile`：管哪些、不碰、交代）→ 最新的交接单（`自动化/交接/`）→「谁在干什么」（`get_overview` 里有）
3. **领一件**：`next_task`——没在跑的单会自己开一张；照你的档案挑（只给「管哪些」里的、跳过「不碰」的），给你一件并记在你名下。领不到会写清是谁在做，**换一件，不等**。领到的那件下面有一段「**为什么做这件**」：S0 一句话 → 哪个大问题 → 目标 / 模块一句话和怎么算做到 → 为了的需求原文 → 怎么验 → 守哪几份戒律。做的时候对着它，别跑偏；没写为了哪条需求的，先问人或起草（10-02，S1-8 S2-34）
4. **先交施工计划，独立审核通过再动手**。档案开启「施工计划必审」时，照 `next_action` 返回调用 `submit_execution_plan(goal, sub, text, files, revision)` 提交或修订同一张；先用 `get_execution_plan` 读取最新版本。待审记录保存在 `自动化/施工计划/`，通过后另存正式 `治理/计划/<目标或模块>/P<号> · 年-月-日 · 标题.md`。计划记录作者、模型、任务、目的、戒律、工具、修改文件范围和验收方法，审核记录保留审核人、时间、理由及所审版本。

   ```
   > 写的：G5 sonnet · 模型 Claude Sonnet 5.5（Claude Code）· 2026-10-02 21:40
   > 哪件：S1-8 S2-45 · 派活看工种（做什么照蓝图原文抄一句）
   > 为了：项目 需-19（需求原文一句）· 目标 S1-8 转得起来
   > 守的戒律：通-x、项-x、模块戒律 · 用到的工具：T3 Git…… · 动到的模块 / 文件：backend/dispatch.py、backend/agents.py……
   > 状态：待审
   ```

   - **准了**：照获准版本和文件范围施工；交付引用正式计划。扩大范围或改计划正文，提交修订重新审，不能沿用旧批准。
   - **打回**：按理由改同一张，先读取最新版本再提交；版本冲突先对照，不覆盖别人的新内容。
   - **等审**：结束当前模型轮次，由外层运行器发现审核结果后再调起。不要让模型循环查文件、执行睡眠命令等审。
   - 审核按岗位和可用性派给另一位员工，不指定 G1，也不允许自审；缺合适审核员时，网页列出缺少岗位和停止原因。是否免审由档案的开关决定，编号和名字没有例外。
5. **改核心先拿锁**：要改 `backend/`、`模板.html`、`界面英文.js`、`治理界面.js`、启动器——先 `claim_task("核心")`（一次一个人），再 `save_checkpoint` 存一档核心；改网页先读 `DESIGN.md`
6. **做、验**：守戒律；照「怎么验」一条条验，记下实际结果。同一件失败到开工单写的次数（默认 2）→ 标「等你」、`ask_human` 写清卡在哪 → 换一件
7. **交付**：`deliver`——本项目按上述 `checks-pass` 策略，实际检查全过就自动验收、算做完，失败自动返工；人打回的按人的理由重做。成功和失败交付都**自动放手**（连核心锁一起），本机 git 自动记一次。
   - **旧流程的验收岗位**：未配置 `checks-pass` 的项目或已有待验收记录仍按原流程处理。`next_task` 可派其他员工的待验收单，验收者实际复跑后用 `review_delivery(code, ok, notes, checks)` 通过或打回，不自验、不改别人做的东西。原流程的三次打回转人工规则仍保留；本项目新交付不因此排队等待。
   - **你的岗位是审核**：`next_action` 给你待审施工计划或草稿（不是你写的、没人在审的）。施工计划须核对需求、修改范围和验收方法，使用 `review_execution_plan(code, ok, why, revision)` 审核读取到的版本；草稿使用 `review_draft(code, ok, why)`。准写为什么准，打回写清哪里不行、怎么改。不替作者改正文，不伪造人的定稿。
   - **你的岗位是规划**：`next_task` 先给你被打回的草稿（照理由用 `propose_draft(revise="草-3", …)` 改同一张），再给你一块还没定稿、还缺东西的目标 / 模块（附这块的方向和需求原文）：起草缺的任务、需求，只起草不改正式文件
   - 顺序：验收 → 审核 → 规划 → 干活；岗位里没有「干活」的，`next_task` 不给你干活的件
8. **报一圈**：`report_run`（在做哪件、做了什么、结果、下一步）；报一圈也算「有动静」
9. **下一件**：再 `next_task`；没有了就写交接单、停

有问题先 `find_answer` 查旧决定；查不到才 `ask_human`，问完跳下一件，不干等。

## 四、报到和档案

- 一个 agent 一份档案、一个文件：`自动化/agent/G1 claude-code.md`。编号 G 号不回收；认人靠名字
- 档案里有：编号 · 名字 · 用什么（哪家）· 一句话 · 报到时间 · **岗位 · 等级 · 上级**（见下面「分工」）· **工种**（程序、网页、文档、翻译、优化，空着 = 未限定）· **管哪些** · **不碰** · **改核心** · **自动运行 · 暂停 · 施工计划必审** · 技能 · 开工的话 · 交代 · 变迁。
- **职责跟着项目变**：人在网页上改；agent 用 `my_profile` 改自己的一句话、交代等说明。岗位、等级、上级、工种、范围、核心权限和自动化开关由人管理。每改一次「变迁」只增一行：何时 · 谁 · 改了什么 · 为什么。
- **人自己定（DIY）**：「自动化 → Agent →＋ 新建 agent」，从样子开始（规划的 · 审核的 · 写代码的 · 写文档的 · 验收的 · 空白）；能提前给还没来的 agent 建好，它来了报同样的名字就接上；能复制、能删（进回收站，能还原；它领着的活放手）
- 名册的灯：在干活（领着活、30 分钟内有动静）· 停了（领着活、30 分钟到 2 小时没动静）· 空着

### 分工：岗位 · 等级 · 上级（10-02，S1-8 S2-38～S2-41；参考三省六部「规划 → 审核能打回 → 派活 → 干活」和公司里的职位、上下级）

本项目从想法到做完：**你定方向和需求 → 规划起草 → 审核 → 你定稿 → 干活并实际检查 → 自动验收 → 做完**。人不满意时打回重做。网页「自动化 → Agent → 组织和流程」保留既有岗位和记录；未配置交付策略的项目沿用原验收流程。

- **岗位**（能兼几个，没写算干活）：
  - **规划**：把需求拆成蓝图里的件（做什么 · 为了哪条需求 · 怎么验，验要机器查得了）、写计划；只用 `propose_draft` 起草，不直接改正式文件
  - **审核**：看草稿区里别人起草的件和计划：准，或打回写清理由；**不审自己写的**
  - **干活**：领件、做、照「怎么验」验、交付单
  - **验收**：处理旧流程的待验收记录，复跑别人交付单里的检查、看东西对不对：过就做完，不过打回写清哪条；**不验自己干的**。`checks-pass` 新交付不等待这个岗位。
  - **带队**：下面的人卡住了先报给它：去看看、帮一把，或让它放手换人
  - 派活不设岗位：开工单、`next_task` 照岗位和档案分活，系统做
- **等级**：见习（只干活，拿不到核心锁；无 `checks-pass` 配置时每件仍需独立或人工验收）· 正式（干活，能当审核或验收）· 资深（能带队、当别人的上级，能改核心）。本项目各等级交付都按实际检查自动验收，权限不因此改变。没写算正式。**带队、当上级都要资深**；降等级前先给下面的人换上级。网页按交付记录建议升级（见习通过 10 件、没被打回 → 正式；正式通过 30 件、打回不到一成 → 资深），升不升人点
- **上级**：每个 agent 有且只有一个上级——别的 agent 或人（写「人」= 直接向人汇报），连成一棵树，不许绕圈。卡住了先报给上级，再报给人
- **只有人改**这三格；领活时 `next_task`、`my_profile` 会告诉你自己的岗位、等级、上级和每个岗位该做什么
- **缺岗位照原准入要求处理**：计划和草稿审核不因交付策略而免除。`checks-pass` 的新交付不需要另配验收员；无配置时仍按原系统和档案决定默认通过、独立复验或人工验收。人仍可查看交付并打回。

## 五、几个 agent 一起干

- **一件一个人**：蓝图里的一件（目标 + S2）同一时间只给一个 agent
- **照档案分工**：「岗位」「工种」「管哪些」「不碰」共同决定谁能领哪类活；任务最前面的〔程序〕〔网页〕〔文档〕〔翻译〕〔优化〕与工种匹配；未标工种的任务保持兼容。「改核心：不能」的拿不到核心锁。
- **一条道一个人**：同一个模块同一时间只给一个 agent。模块蓝图的件，道就是模块名；总蓝图的件，道是 S1 写的「动到的模块」，没写就是这一件自己
- **核心锁**：改核心文件先拿，一次一个人；交付时自动放
- **卡住了往上报**（10-02，S1-8 S2-36）：领着活半小时没动静 → 下次你来时提醒你，同时报给你的上级（上级下次 `next_task` 最前面写「叫你是因为……」，它可以看看、帮一把，或 `release_task(…, for_agent="G2")` 让你放手）；一小时还不动 → 人那边也看得到（总览「要你的」）
- **2 小时没动静就算放手**：没报一圈、没交付、没再领，别人能接。半路不做了用 `release_task`（`note` 写为什么，接手的人看得到）
- **别动别人正在改的**：别人领着的模块文件夹、别人拿着核心锁时的核心文件，不碰
- **本机 git 记账**：交付时自动提交一次，作者写你的名字；只提交这些——交付单、这件的蓝图文件、交付单里列的文件、记录（交付、日志、交接、开工单、计划）、你领的模块文件夹、你拿着核心锁时的核心文件。**只在这台电脑，不推送、不上传**
- **没接接口（MCP）的 agent** 看不到也领不了，别跟别人同时开；它照文件做、写交接单
- **清理的活**（10-03，S1-8 S2-62、S2-63；作者：「我的想法是重铸由agent来做」）：有「规划」岗位的会领到「写摘要」（digest_material 看材料，只照材料写、每句写出处，write_digest 交）和「写重写单」（读正本全文，合并重复、去掉过时的、把抄来的换成指向原处，propose_rewrite 出单，不自己换上）；有「审核」岗位的会领到「审重写单」（看对照、核出处，review_rewrite 行就换上、不行写清哪里不对，不审自己出的）。需求、戒律、目标的单只能出，换上等人。开工先读 get_overview 最前面的「项目现在的样子」
- **档位**（10-03，S1-8 S2-57、S2-58；设置 → 自动化）：1 一条线 · 2 主干上几个人 · 3 分枝并行 · 4 优中选优。档位 3、4 时，全自动开工自己长枝、派人：主干上该开枝的件写着「世界树:比-n」在领，主干的人别领；被派到枝上的照常领那件、做、交付（交付单记在枝上），检查全过就自动结果实，不用再调 bear_fruit；有「验收」岗位的员工会领到「挑果实」（`pick_fruit`，看比较单里每根枝的 demo、检查、`branch_changes`，挑一根合，都不行就空着 branch 打回，写清哪里不对；不挑自己做的）。拿核心锁时程序照设置自动存一档、交付后也存，不用自己再存
- **在世界树的枝上干**（10-03，S1-8 S2-55、S2-56）：要大改、要试一个方向、或几个人都要改核心时，G1 用 `grow_branch` 从一档（或现在）长一根枝——整份项目放在项目旁边的「<项目名> 世界树/枝-n 名字/」，自己的库、核心锁、认领、存档；`assign_to_branch` 把员工派上去，窗口开在主干网页终端里、标题「枝-n · G5 名字」。在枝里开的 agent 只改枝（`world_tree` 一调就知道自己在哪根枝上）；照常领活、交付（交付单、日志记在枝上）。干完 `bear_fruit`：写清 demo 怎么看、看什么，检查里写跑过的测试。G1 验收：开枝的网页看 demo、在枝里跑测试、`branch_changes` 看改动；过了 `merge_branch`（合前合后各存一档；合不开的不覆盖，放进 `自动化/世界树/枝-n/冲突/`，G1 照着手合、合完在主干跑全部测试），不过 `reject_fruit` 写清哪里不对，方向不对 `cut_branch`。改到核心的枝，主干核心锁在别人手里时合不了。合并会把主干里这几个文件现在的样子一起记进本机 git，所以合之前主干上这几个文件最好已经交付记账

## 六、交接

- **走之前**写一张交接单：`自动化/交接/H<号> · 年-月-日 · 你的名字.md`，7 件事——做了什么（为了哪条需求 / 哪件 S2）· 改了哪些文件 · 验了什么、实际结果 · 没做完的 · 没验证的和有风险的 · 下一步建议 · 等人定的事
- **来了**先读最新那张和「谁在干什么」；别人领着的不抢

## 七、网页自己盯着（监管）

规矩不只靠 agent 自觉：网页后台一直看着项目里的文件，对照谁领着活、谁拿着核心锁，照七条看——没拿锁改核心、删东西没进回收站、改了人的笔记、改了方向文件、自动化在跑时改了没人领着的模块、领着活不动、干活不报到。发现了**不停**：记下来、亮灯；删文件、改笔记、改方向的发到问答等人拍板；你下次领活、报一圈、交付时，返回里有「监管提醒」，照着改就行。

## 八、只在这两类事上停

- **彻底删除、公开发布**（上传、发帖、推送到网上）
- **改方向**：S0、S1、需求、戒律正文——新想法用 `add_idea` 记成想法，人来定
- **加任务、加需求**：做着做着想加一件 S2、一条需求，用 `propose_draft` 放进草稿区（`治理/草稿/`），不直接往表里加行；人在蓝图「草稿区」点「行」才收进去，编号程序排。放进去就接着做别的，不用等

停了**不干等**：写清楚（`ask_human`）、跳过这件，接着做别的。

**不停，但要记**：
- 装软件：只从官方来源装；装了记日志、写工具卡
- 挪进回收站（能还原）
- 改核心：先存一档核心；改完日志记「改了核心」
- 要花钱的：agent 付不了——记下来，跳过

## 九、人怎么看、怎么管

- **看**：网页「自动化」一进来是**总览**：要你的（真要人点的，带按钮）· 一个 agent 一张卡片 · 四个大数 · 四张 14 天小图 · 最近的动静和离全自动还差什么；左边四组——自动化（总览、等你的）· 干活（任务看板、开工单、离全自动还差什么、流程）· Agent（名册和每个人的档案）· 记录（交付、每圈日志、监管、交接单、后台任务、本机 git）；任务看板点一张卡是一件的详情（为什么那条链、等谁、卡着谁、来龙去脉）；笔记本「日志」；「存档」
- **定 agent**：新建、改职责、改管哪些 / 不碰 / 能不能改核心、复制、删——都在 Agent 管理
- **不满意**：在交付单上点「打回」、写理由；那件回到「在做」，下一个 agent 照理由改
- **叫停**：「自动化」页开工单上点「叫停」；agent 不再自己开新单。想接着跑：点「交给 agent」，或在对话里说一句
- **排先后**：在蓝图里挪；**改方向**：自己改 S0、S1、需求、戒律，或在对话里说

## 十、外层运行器怎么接着推进

网页「自动化 → 窗口」保留员工终端和输出，并显示总开关、同时运行上限（默认 3）、每人的当前任务、停止原因、缺少岗位、施工计划和最近审核。三条导航和项目模块不变。

- **参加自动运行**：在员工档案开启「自动运行」、取消「暂停」，配好岗位、工种、范围、模型和是否需要施工计划审核。员工编号没有特权；审核、验收都不能给本人。
- **平台不调用模型 API**：本机 Python 外层运行器检查 `next_action`，有可执行动作时启动档案指定的真实 Codex CLI。每个模型轮次只处理一项：提交计划、审核、施工交付或旧流程验收；本项目新交付按 `checks-pass` 自动验收或返工。CLI 的登录、模型和可用工具以本机安装环境为准；其他 CLI 按各自适配器接入，不把终端打开当作模型已经接通。
- **等待不占模型轮次**：等审、旧流程等验收、等锁、暂无合适任务时结束模型轮次，外层检查状态，条件满足后再启动下一轮。不要在提示词里要求模型睡眠、反复问「好了没」，也不依赖 G1 来改名、派下一件或作唯一验收员。
- **人管边界，岗位接工作**：方向仍由人定。系统按档案和现有认领机制找下一位；缺岗位、缺工具、遇到暂停或达到次数上限，就显示原因。不会替缺席的人写批准，不会把没跑的检查写成通过。
- **停和恢复**：关闭总开关、暂停员工或关闭该员工窗口后，不再派新任务；外层运行器向当前模型及其子进程发停止指令，留下停止原因和交接记录后退出，不把中断的工作当成成功。等审核、旧流程验收或锁释放时自然退出，保留未交付施工认领、放开核心与审核验收锁；真正叫停、异常或到上限时放手，恢复时根据人的明确派活普通记录、原授权版本及任务状态重新核对接续。授权或任务方向变化须重新派活；已完成或旧流程已交待复验的不重复施工。连续失败留下的阻塞只能通过明确的“恢复自动化”解除，活窗口预算不清，不无限重试。
- **留记录**：运行状态用 `report_employee_runtime(state)` 更新；收工通过 `write_handover(text)` 留交接，记录实际做过、验过、没验的内容。文件、计划、交付和日志中的员工身份要与档案一致。

本节说明运行方式，不代表已经通过真实 CLI 的整链试跑。是否验收通过看对应交付单及其实际检查结果；模拟开窗、脚本语法检查、真实 agent 完成任务须分别记录。
